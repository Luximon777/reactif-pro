Le flux CV **fonctionne globalement en production** (222 jobs `completed`, dernier succès aujourd'hui à 09:40 UTC). La panne rapportée par l'utilisateur correspond à des **timeouts de lecture MongoDB (Atlas) intermittents**, PAS à un problème de code CV, de build, de dépendance manquante, de secret manquant ou de budget LLM épuisé.

- **LLM (gpt-5.2 via emergentintegrations/LiteLLM) : OK.** Nombreux `LiteLLM completion() model= gpt-5.2; provider = openai` suivis de `Completed Call`. Aucune erreur 402/429. Exemple de succès récent :

## Cause racine
Timeouts de lecture intermittents vers le cluster MongoDB Atlas géré par Emergent (`customer-apps-shard-00-01.vxphtw.mongodb.net:27017: The read operation timed out`). Ils font échouer certains jobs d'analyse CV et renvoient 500 sur les endpoints de polling (`/api/cv/analyze/status`, `/api/coach/progress`). 

Facteur aggravant possible (non confirmé par métrique directe) : le CPU limité de tier_0 (250m) pendant une analyse CV lourde (LLM + OCR PyMuPDF) peut throttler le process et contribuer aux timeouts côté client pymongo. À traiter comme piste, pas comme cause prouvée (pas d'OOM, exit 0).

## Correctifs recommandés
1. **Code (E1)** — Rendre le flux CV résilient aux timeouts Mongo transitoires :
   - Configurer le `MongoClient` avec `retryReads=true`, `serverSelectionTimeoutMS` et `socketTimeoutMS` plus tolérants, et un `timeoutMS` raisonnable.
   - Entourer les écritures/lectures du worker d'analyse CV et des endpoints de statut d'un retry sur `NetworkTimeout`/`AutoReconnect`.
   - Réconcilier les 8 jobs bloqués en `analyzing` (les repasser en `failed`/`retry` pour débloquer le polling côté client).
   - Non reproductible en sandbox éphémère (nécessite l'Atlas réel + secrets) → à appliquer dans l'env source puis redéployer.
2. **Platform (escalade Emergent)** — Investiguer les timeouts récurrents côté Atlas géré (`customer-apps-shard-00-01.vxphtw.mongodb.net`). Si récurrent après le durcissement code, ticket support avec deployment_id `ad9b6b03-971a-42b8-b15b-ee401e317181` / job_id `90063908-4547-4619-a39d-4ae3b0877c31`.
3. **Utilisateur (décision)** — Choisir de redéployer pour livrer les features manquantes (reconversion.py, ubuntoo_v2.py) ET embarquer le correctif de résilience ci-dessus. Le redéploiement seul ne corrige pas les timeouts Atlas. Optionnel/précaution : évaluer une montée de tier (CPU) si les timeouts coïncident avec des analyses CV lourdes.
