## 4. Cause racine (confirmée dans le code source — backend/server.py)
`_run_cv_analysis()` appelle `_extract_text_from_bytes()` (ligne ~4001) :

```python
elif filename.lower().endswith((".docx", ".doc")):
    import docx
    doc = docx.Document(io.BytesIO(content))
    for para in doc.paragraphs:
        text += para.text + "\n"
```

Puis (ligne ~4057) :
```python
if (not cv_text or len(cv_text) < 50) and not text_ready and filename.lower().endswith(".pdf"):
    # fallback OCR vision — RÉSERVÉ AU PDF
    ...
if not cv_text or len(cv_text) < 50:
    # -> status "failed" + message "pas assez de texte exploitable"
```

**Problème :** `python-docx` via `doc.paragraphs` ne lit **que** les paragraphes du corps. Il **n'extrait pas** le texte contenu dans :
- les **tableaux** (`doc.tables`),
- les **zones de texte / formes** (text boxes, drawing canvas),
- les **en-têtes/pieds de page**.

Les deux CV de syl67 sont des modèles mis en page (« Commerciale », « Chef de produit touristique ») dont le contenu est très probablement en tableaux/zones de texte → `doc.paragraphs` renvoie < 50 caractères → rejet.

De plus, le **fallback OCR (`_ocr_pdf_via_vision`) est conditionné à `.endswith(".pdf")`** : les `.docx` ne bénéficient d'**aucun repli**. Un `.docx` « pauvre en paragraphes de corps » est donc rejeté même s'il contient du texte réel ailleurs.

## 5. Même cause que le RCA 39ff6a3a ? → NON, cause DIFFÉRENTE
- RCA 39ff6a3a = **NetworkTimeout Atlas intermittent** (`customer-apps-shard-00-01.vxphtw.mongodb.net:27017: The read operation timed out`), jobs bloqués en `analyzing`.
- Ce timeout Atlas S'EST bien produit aujourd'hui, mais sur un **AUTRE compte** : Nathalie HUNSINGER, token `17d5b2b4`, job `c4701d94-9d9e-4b38-b601-f0b5a3c14b98`, log ERROR `2026-10-06 09:36:32 ... The read operation timed out`.
- Les jobs de **syl67 n'ont JAMAIS touché Atlas sur une erreur** : ils échouent en amont, à l'extraction de texte DOCX, avec `status=failed`/`step=Erreur` (et non `analyzing` figé).

**Conséquence pratique :** le correctif de résilience Mongo prêt dans le code (retryReads / mongo_retry / réconciliation au démarrage) **ne corrigera PAS** le problème de syl67. Redéployer réglera les timeouts Atlas intermittents (bénéfique pour des cas type Nathalie), mais les `.docx` de syl67 continueront d'être rejetés tant que l'extraction DOCX n'est pas améliorée.

## 6. Correctifs recommandés (à appliquer par E1 dans le code source)
Dans `backend/server.py`, `_extract_text_from_bytes()` pour les `.docx` :
1. Concaténer aussi le texte des **tableaux** : `for t in doc.tables: for row in t.rows: for cell in row.cells: text += cell.text`.
2. Récupérer le texte des **zones de texte/formes** (XML `w:txbxContent` / drawing) et des **en-têtes/pieds** (`doc.sections[*].header/footer`).
3. Étendre le **fallback OCR** aux `.docx` pauvres en texte (convertir/rendre en image puis `_ocr_pdf_via_vision`-like), ou au minimum convertir DOCX→PDF avant OCR.
4. Rejeter proprement le `.doc` binaire legacy (python-docx ne le lit pas) avec un message explicite.

⚠️ **Non reproduit avec les fichiers réels** : les `.docx` d'origine de syl67 ne sont pas accessibles dans le sandbox (pas de secrets/pièces). Le diagnostic code (branche < 50 car. + absence de lecture tables/text boxes + OCR limité au PDF) est confirmé par lecture de `server.py` sur la source de ce run. La cause exacte côté fichier (contenu en tableaux/zones de texte vs fichier réellement vide) ne peut être tranchée à 100 % sans les fichiers — mais deux modèles de CV distincts échouant à l'identique pointent fortement vers la limitation d'extraction DOCX.

## 7. Contournement utilisateur immédiat
syl67 peut ré-uploader son CV en **PDF** (qui bénéficie du fallback OCR vision) ou en **.txt**, en attendant le correctif d'extraction DOCX.
